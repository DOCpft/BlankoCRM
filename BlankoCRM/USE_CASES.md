## 1. Аутентификация и регистрация

### UC-A1. Регистрация по email и паролю
**Актор:** Мастер. **Endpoint:** `POST /api/auth/register`.
**Шаги:**
1. Мастер передаёт `name?`, `email`, `password`, `organizationName?`.
2. Система валидирует данные (email, пароль ≥ 6).
3. Создаётся `Organization` (генерируется уникальный `slug`).
4. Создаётся `AppUser` (email как `UserName`).
5. Создаются 5 настроек напоминаний `MasterReminderSetting` (offsets 1,3,6,12,24; включены 6,3,1).
**Результат:** 201. Мастер зарегистрирован.

### UC-A2. Регистрация с уже занятым email
**Шаги:** email уже существует.
**Результат:** ошибка Identity → `ValidationException` (400). Данные не сохраняются (транзакция откатывается).

### UC-A3. Вход по email и паролю
**Актор:** Мастер. **Endpoint:** `POST /api/auth/login`.
**Шаги:** корректные `email` + `password`.
**Результат:** 200 `{ token, name, email }` (JWT на 7 дней).

### UC-A4. Вход с неверными данными
**Результат:** 401 (`UnauthorizedException`).

### UC-A5. Вход через VK Mini App (существующий пользователь)
**Endpoint:** `POST /api/auth/vk-mini-app`.
**Шаги:** система проверяет подпись VK; находит `AppUser` по `VkUserId`.
**Результат:** 200 `{ token, name, email }`.

### UC-A6. Вход через VK Mini App (новый пользователь — авто-регистрация)
**Шаги:** подпись валидна, `VkUserId` не найден → создаётся `Organization` + `AppUser` (`UserName = vk_{id}`, без email) + 5 настроек напоминаний.
**Результат:** 200 `{ token, ... }`.

### UC-A7. Недействительная подпись VK
**Результат:** 401 (`UnauthorizedException` — «Недействительная подпись VK»).

## 2. Клиенты

### UC-C1. Получить список клиентов
**Endpoint:** `GET /api/clients/all`. **Результат:** 200 `[ClientDto]`, отсортированы по имени.

### UC-C2. Поиск клиентов
**Endpoint:** `GET /api/clients/all?search=...`. Ищет подстроку в имени или телефоне.
**Результат:** 200 — отфильтрованный список.

### UC-C3. Получить клиента по ID
**Endpoint:** `GET /api/clients/{id}`. **Результат:** 200 `ClientDto`; если не найден — 404.

### UC-C4. Создать клиента
**Endpoint:** `POST /api/clients/create`. Тело: имя (обязательно), телефон, контакты, дата рождения, заметки, салон.
**Шаги:** телефон нормализуется; создаётся `Client` + контакты (по одному на тип).
**Результат:** 201 `ClientDto`.

### UC-C5. Создать клиента с дублирующимся телефоном
**Результат:** 409 (уникальность `(OrganizationId, Phone)`).

### UC-C6. Создать клиента с повторяющимися типами контактов
**Результат:** 400 (FluentValidation — «Типы контактов не должны повторяться»).

### UC-C7. Обновить клиента (частично)
**Endpoint:** `PUT /api/clients/update/{id}`. Обновляет только переданные поля.
**Результат:** 204.

### UC-C8. Синхронизация контактов при обновлении
**Шаги:** переданный список контактов синхронизируется по типу: отсутствующие удаляются, новые добавляются, изменённые обновляются.
**Результат:** 204.

### UC-C9. Удалить клиента
**Endpoint:** `DELETE /api/clients/delete/{id}`. **Результат:** 204.

### UC-C10. Удалить клиента, у которого есть записи
**Результат:** 409 («Нельзя удалить клиента с существующими записями»).

### UC-C11. Некорректный телефон
**Результат:** 400 (недопустимые символы / длина).

### UC-S2. Получить услугу по ID — `GET /api/services/{id}` → 200; не найдена → 404.
### UC-S3. Создать услугу — `POST /api/services` (название, длительность 1–1440, цена 0–999999.99, описание, салон) → 201.
### UC-S4. Создать услугу с дублирующимся названием в организации → 409.
### UC-S5. Обновить услугу — `PUT /api/services/{id}` (частично) → 204.
### UC-S6. Удалить услугу — `DELETE /api/services/{id}` → 204.
### UC-S7. Удалить услугу, используемую в записях → 409.

## 4. Расписание (слоты)

### UC-Sch1. Получить слот по ID — `GET /api/schedule/{id}` → 200 `ScheduleDto`; не найден → 404.
### UC-Sch2. Получить расписание за период — `GET /api/schedule/get/period?dtFrom=&dtTo=` → 200 `[ScheduleDto]`; `dtFrom >= dtTo` → 400.

### UC-Sch3. Добавить свободный слот
**Endpoint:** `POST /api/schedule/free`. Тело: `{ startTime, endTime, salonId? }`.
**Шаги:** валидация `endTime > startTime`; проверка пересечения со свободными слотами.
**Результат:** 201 `ScheduleDto`.

### UC-Sch4. Добавить свободный слот, пересекающийся с существующим → 409.

### UC-Sch5. Добавить занятый слот
**Endpoint:** `POST /api/schedule/occupied`. Создаёт запись (через `CreateWithScheduleAsync`) и связанный слот.
**Результат:** 201 `ScheduleDto` (со вложенной `AppointmentDto`).
**Ошибки:** конфликт времени → 409; клиент/услуга не найдены → 404.

### UC-Sch6. Массово добавить свободные слоты
**Endpoint:** `POST /api/schedule/free/bulk`. Проверка пересечений внутри пакета и с БД.
**Результат:** 200 `[ScheduleDto]`. Пустой список → 200 `[]`.

### UC-Sch7. Обновить слот (сдвинуть время) — `PUT /api/schedule/{id}` → 204.
**Ошибки:** пересечение с другим слотом/записью → 409.

### UC-Sch8. Обновить запись у свободного слота
**Результат:** 400 (`ValidationException` — «Нельзя обновить запись у свободного слота»).

### UC-Sch9. Удалить слот — `DELETE /api/schedule/{id}` → 200 `bool`.
### UC-Sch10. Массово удалить слоты — `DELETE /api/schedule/delete/bulk` (тело `[Guid]`) → 200 `int` (сколько удалено); пустой список → 400; ничего не удалено → 404.

## 5. Записи — управление мастером

### UC-App1. Получить запись по ID — `GET /api/appointments/{id}` → 200; не найдена → 404.
### UC-App2. Получить все записи организации — `GET /api/appointments/all` → 200.
### UC-App3. Получить записи за день (календарь) — `GET /api/appointments/calendar?date=` → 200.
### UC-App4. Получить активные Pending-заявки — `GET /api/appointments/pending` → 200.

### UC-App5. Создать запись (Scheduled)
**Endpoint:** `POST /api/appointments`. Тело: `{ clientId, services, startTime, notes?, salonId? }`.
**Шаги:** проверка клиента/услуг; расчёт длительности и `EndTime`; проверка пересечения; создание `Appointment` + `Schedule`; удаление пересекающихся свободных слотов.
**Результат:** 201 `AppointmentDto`.

### UC-App6. Создать запись с пересечением времени → 409 («Время записи уже занято»).

### UC-App7. Обновить запись — `PUT /api/appointments/{id}` (клиент, салон, услуги, время, заметки) → 204; пересечение → 409.

### UC-App8. Обновить Pending-заявку
**Результат:** 409 («Ожидающую заявку нельзя редактировать»).

### UC-App9. Удалить запись — `DELETE /api/appointments/{id}` → 204; освобождает слот.

### UC-App10. Удалить Pending-заявку → 409.

### UC-App11. Отменить запись — `PATCH /api/appointments/{id}/cancel`
Переход `Pending`/`Scheduled` → `Cancelled`; для Scheduled освобождается слот.

### UC-App12. Подтвердить заявку (confirm)
**Endpoint:** `POST /api/appointments/{id}/confirm`.
**Шаги:** проверка статуса `Pending`, срок не истёк, нет пересечения, нет уже существующего слота → статус `Scheduled` + создание `Schedule` + удаление пересекающихся свободных слотов.
**Результат:** 204.

### UC-App13. Подтвердить истёкшую заявку → 409 («Срок действия заявки истёк»).
### UC-App14. Подтвердить заявку с пересечением времени → 409 («На это время уже есть подтверждённая запись»).
### UC-App15. Отклонить заявку — `POST /api/appointments/{id}/reject` → `Pending` → `Rejected`; 204.
### UC-App16. Завершить запись — `POST /api/appointments/{id}/complete` → `Scheduled` → `Completed`; 204.
### UC-App17. Отметить «не пришёл» — `POST /api/appointments/{id}/no-show` → `Scheduled` → `NoShow`; 204.
### UC-App18. Недопустимый переход статуса (например, complete у Pending) → 409.

## 6. Публичные заявки клиента (VK Mini App)

**Общие предусловия:** маршрут `/api/public/{organizationSlug}/appointments`; организация определяется по `slug`; подпись VK валидна.

### UC-P1. Получить свободные слоты
**Endpoint:** `GET .../slots?from=&to=&limit=`.
**Результат:** 200 `[PublicFreeSlotDto]` (свободные слоты в периоде).
**Ошибки:** `from >= to` → 400; период > 31 дня → 400; limit вне 1..500 → 400.

### UC-P2. Получить свои записи
**Endpoint:** `POST .../mine` (тело `{ vkParams }`). Находит клиента по VK ID.
**Результат:** 200 `[AppointmentDto]` (активные `Pending` + `Scheduled`); если клиента нет — 200 `[]`.

### UC-P3. Создать заявку (успех)
**Endpoint:** `POST .../appointments`. Тело: `{ freeSlotId, vkParams, name, phone?, services, startTime, notes? }`.
**Шаги:**
1. Проверка подписи VK, rate limit, валидация имени/услуг/времени.
2. Загрузка услуг организации, расчёт длительности и `EndTime`.
3. Блокировка свободного слота; проверка, что заявка помещается в слот.
4. Нахождение/создание клиента.
5. Проверка лимита активных заявок (≤ 5) и дубликата на то же время.
6. Создание `Appointment` со статусом `Pending` (`ExpiresAt = now + 24ч`).
7. Отправка Telegram-уведомления мастеру.
**Результат:** 201 `AppointmentDto`.

### UC-P4. Недействительная подпись VK → 401.
### UC-P5. Заявка на прошедшее время → 400 («Нельзя создать заявку на прошедшее время»).
### UC-P6. Услуга не найдена в организации → 404.
### UC-P7. Выбранный свободный слот уже занят → 409 («Выбранный свободный интервал больше недоступен»).
### UC-P8. Заявка не помещается в слот → 400.
### UC-P9. У клиента уже 5 активных заявок → 429 (`TooManyRequestsException`).
### UC-P10. Дублирующаяся заявка на то же время → 409.
### UC-P11. Клиент найден по VK ID → используется существующая карточка (при необходимости дополняется телефон).
### UC-P12. Клиент найден только по телефону → добавляется контакт VK.
### UC-P13. Клиент не найден → создаётся новая карточка с контактом VK.
### UC-P14. VK ID и телефон привязаны к разным карточкам → 409.

### UC-P15. Отозвать заявку (withdraw)
**Endpoint:** `POST .../appointments/{id}/withdraw` (тело `{ vkParams }`).
**Условия:** заявка принадлежит этому клиенту, статус `Pending`, срок не истёк.
**Результат:** 204; статус → `Withdrawn`.
**Ошибки:** не своя/не найдена → 404; не `Pending` → 409; истёк срок → 409.

### UC-P16. Отозвать чужую заявку → 404.

### UC-P17. Отменить заявку/запись (cancel)
**Endpoint:** `POST .../appointments/{id}/cancel` (тело `{ vkParams }`).
- `Pending` → `Cancelled` (если не истёк срок).
- `Scheduled` → `Cancelled` + освобождение слота.
- Прочие статусы → 409.

### UC-P18. Превышение rate limit → 429 (по IP и/или по VK ID).

## 7. Telegram: привязка и уведомления

### UC-T1. Сгенерировать ссылку привязки Telegram
**Актор:** Мастер. **Endpoint:** `POST /api/profile/telegram/link`.
**Шаги:** генерируется код (8 символов), сохраняется `TelegramLinkCode` + `ExpiresAt = now + 10 мин`.
**Результат:** 200 `{ url: "https://t.me/{bot}?start={code}", botUsername }`.

### UC-T2. Отвязать Telegram — `DELETE /api/profile/telegram/link` → 204 (сбрасывает `TelegramChatId` и код).

### UC-T3. Получить статус привязки — `GET /api/profile/telegram/status` → 200 `{ linked, notificationsEnabled }`.

### UC-T4. Нажать Start с валидным кодом
**Актор:** Клиент (получатель уведомлений). **Вход:** webhook `/start {code}`.
**Шаги:** система находит `AppUser` по коду (код не истёк) → сохраняет `TelegramChatId`, очищает код → бот отвечает «Теперь уведомления о записях будут приходить Вам сюда! Хорошей работы)».
**Результат:** чат привязан.

### UC-T5. Нажать Start с невалидным/истёкшим кодом → бот: «Код недействителен. Сгенерируйте новый в личном кабинете».

### UC-T6. Нажать Start без кода → бот: «Привет! Чтобы привязать уведомления, откройте личный кабинет в CRM».

### UC-T7. Мастер получает уведомление о новой заявке
**Триггер:** создание Pending-заявки (UC-P3). Сообщение: имя клиента, услуги, время (в таймзоне мастера), заметки.
**Условие:** у мастера заполнен `TelegramChatId` и включены уведомления.

### UC-T8. Мастер получает напоминание о записи
**Триггер:** фоновый worker. Сообщение: «Напоминание: через N ч. запись…».

### UC-T9. Бот заблокирован мастером (403)
**Триггер:** отправка уведомления вернула 403 (`TelegramForbiddenException`).
**Результат:** `TelegramChatId` сбрасывается в null, логируется Warning, основной флоу (создание заявки) продолжается без ошибки.

### UC-T10. Webhook с неверным секретом → 401.
### UC-T11. Webhook с верным секретом → всегда 200 (даже при ошибке парсинга тела).

## 8. Профиль и настройки мастера

### UC-Pr1. Получить настройки напоминаний — `GET /api/profile/reminder-settings` → 200 `[ReminderSettingDto]` (отсортированы по offset).
### UC-Pr2. Обновить настройки напоминаний — `PUT /api/profile/reminder-settings` (тело `{ settings: [{offsetHours, enabled}] }`) → 204. Обновляются только переданные offset'ы, остальные не трогаются.

### UC-Pr5. Невалидный часовой пояс → 400 (`ValidationException`).

## 9. Фоновые/системные сценарии

### UC-Sys1. Просроченная Pending-заявка автоматически отменяется
**Триггер:** `PendingAppointmentExpirationWorker` (раз в 1 минуту).
**Шаги:** находит заявки со статусом `Pending` и `ExpiresAt <= now`, переводит в `Cancelled` (пакетами по 100).
**Результат:** заявка более недоступна клиенту и не отображается в списке `pending`.

### UC-Sys2. Отправка напоминания за offset часов
**Триггер:** `AppointmentReminderWorker` (раз в 5 минут).
**Шаги:** для каждого offset из {1,3,6,12,24} ищет Scheduled-записи в окне `[now + offset − 5 мин, now + offset + 5 мин]`; проверяет, что offset включён у мастера и напоминание ещё не отправлялось; отправляет; фиксирует `AppointmentReminderLog`.
**Результат:** мастер получает напоминание.

### UC-Sys3. Повторное напоминание не отправляется
**Гарантия:** уникальный индекс `(AppointmentId, OffsetHours)` + проверка `ExistsAsync` перед отправкой.

### UC-Sys4. Ошибка фонового сервиса не прерывает работу
Оба worker'а ловят исключения, логируют и продолжают по расписанию.
