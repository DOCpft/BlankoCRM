# AI Development Specification (AI-DEV-SPEC)

> Регламент разработки BlankoCRM с использованием ИИ-ассистентов.
> Цель — обеспечить качество, воспроизводимость и прозрачность ИИ-assisted разработки.

---

## 1. Назначение

Документ описывает **обязательный процесс** разработки функциональности с использованием ИИ-ассистентов (ChatGPT, Claude, GitHub Copilot, Cursor и т.п.).

Регламент решает следующие задачи:
- **Снижение риска галлюцинаций** ИИ (выдуманные API, методы, поля).
- **Гарантия соответствия бизнес-требованиям** и архитектуре проекта.
- **Прозрачность решений** — каждое изменение можно отследить и объяснить.
- **Воспроизводимость** — процесс повторяем для любой задачи.

---

## 2. Область применения

Регламент применяется для задач, которые:
- Затрагивают **бизнес-логику** (сервисы, доменные правила, валидация).
- Изменяют **схему БД** (сущности, связи, миграции).
- Меняют **публичный API** (контроллеры, DTO).
- Затрагивают **инфраструктуру** (аутентификация, мультитенантность, транзакции).

> **Исключение:** тривиальные задачи (правки текста, переименование переменных, добавление комментариев) можно выполнять без полного цикла.

---

## 3. Роли

| Роль | Ответственность |
|------|-----------------|
| **Разработчик (человек)** | Формулирует задачу, проверяет каждый шаг, принимает финальные решения, несёт ответственность за код |
| **ИИ-ассистент (chat)** | Структурирует задачу, составляет промпты, перепроверяет требования |
| **ИИ-агент (IDE / agent mode)** | Реализует код по утверждённому промпту, коммитит изменения |

**Ключевой принцип:** ИИ **никогда не принимает решения** — он предлагает, а человек утверждает.

---

## 4. Процесс (Workflow)

### Шаг 1. Описание задачи

**Что делает разработчик:**
- Формулирует задачу свободным текстом: что нужно, зачем, для кого.
- Прикладывает контекст: ссылки на файлы, скриншоты, примеры.

**Что делает ИИ:**
- **Структурирует задачу** на основе текущего проекта.
- Разбивает на подзадачи.
- Указывает предполагаемые затронутые файлы/слои.

**Результат:** структурированная постановка задачи.

---

### Шаг 2. Проверка постановки задачи разработчиком

**Что делает разработчик:**
- Проверяет, что ИИ **правильно понял** бизнес-логику.
- Уточняет неясные моменты.
- Исправляет ошибки в понимании архитектуры.

**Критерии приёмки:**
- ✅ Все бизнес-требования отражены.
- ✅ Указаны все затронутые слои.
- ✅ Нет выдуманных сущностей/полей/методов.

**Если есть расхождения →** возврат к Шагу 1 с уточнениями.

---

### Шаг 3. Кросс-проверка ИИ

**Что делает разработчик:**
- Отправляет структурированную задачу **обратно ИИ** с запросом:
  > «Проверь постановку задачи на полноту и корректность относительно бизнес-требований и текущего кода проекта. Укажи противоречия, упущения, риски.»

**Что делает ИИ:**
- Находит противоречия.
- Указывает, чего не хватает.
- Предлагает улучшения.

**Результат:** уточнённая постановка задачи.

---

### Шаг 4. Составление промпта

**Что делает разработчик:**
- Просит ИИ составить промпт для реализации, учитывая:
  - **Все бизнес-требования.**
  - **Специфику проекта** (мультитенантность, UnitOfWork, OrganizationContext, глобальные фильтры).
  - **Архитектурные слои** (Core / Infrastructure / Application / Web).
  - **Best practices** (SOLID, Clean Architecture, async/await, CancellationToken).
  - **Стандарты кодирования** (naming, комментарии, XML-doc).

**Что делает ИИ:**
- Составляет **детальный промпт** с шагами реализации.
- Указывает, какие файлы изменить/создать.
- Описывает критерии приёмки.

**Результат:** готовый к использованию промпт.

---

### Шаг 5. Ручная проверка промпта

**Что делает разработчик:**
- Читает промпт.
- Проверяет **соответствие бизнес-требованиям** (сверяет со Шагом 1).
- Проверяет **архитектурную корректность** (слои, паттерны).
- Ищет упущения (edge cases, ошибки, безопасность).

**Критерии приёмки:**
- ✅ Покрыты все бизнес-требования.
- ✅ Учтена специфика проекта.
- ✅ Нет «выдуманных» API.
- ✅ Указаны критерии приёмки.

**Если есть замечания →** Шаг 6.

---

### Шаг 6. Правки промпта (при необходимости)

**Что делает разработчик:**
- Просит ИИ внести правки в промпт.
- Повторяет Шаг 5 после правок.

**Цикл повторяется**, пока промпт не будет полностью соответствовать требованиям.

---

### Шаг 7. Финальная перепроверка промпта ИИ

**Что делает разработчик:**
- Отправляет финальный промпт **обратно ИИ** (в том же чате) с запросом:
  > «Перепроверь промпт досконально. Если всё соответствует — подтверди. Не отправляй промпт заново, только проверка.»

**Что делает ИИ:**
- Анализирует промпт.
- Либо подтверждает, либо указывает замечания.

**Если ИИ находит замечания →** возврат к Шагу 5.
**Если подтверждает →** переход к Шагу 8.

---

### Шаг 8. Реализация в агентном режиме

**Что делает разработчик:**
- Копирует промпт в **агентный режим** (Cursor Agent, Copilot Workspace, Claude Dev и т.п.).
- Включает **обязательные подтверждения после каждого шага**.

**Что делает ИИ-агент:**
- Выполняет **один шаг** промпта.
- **Останавливается** и ждёт подтверждения.
- Только после явного «продолжай» — переходит к следующему шагу.

**Обязательные действия разработчика после каждого шага:**
1. **Проверить код глазами.**
2. **Запустить сборку** (`dotnet build`).
3. **Запустить тесты** (если есть).
4. **Отправить сводку по шагу в чат** с ИИ-ассистентом с запросом:
   > «Проверь, соответствует ли выполненный шаг требованиям промпта. Укажи отклонения.»
5. **Получить подтверждение** и только затем переходить к следующему шагу.

**Если есть отклонения →** возврат к Шагу 4 (обновить промпт) или исправление вручную.

---

## 5. Критерии завершения задачи

Задача считается завершённой, когда:
- ✅ Все шаги промпта выполнены.
- ✅ Проект собирается без ошибок.
- ✅ Все бизнес-требования реализованы.
- ✅ Пройдены ручные тесты (см. чек-лист в `TESTING.md`).
- ✅ Код соответствует архитектуре и стандартам.
- ✅ Обновлена документация (если требуется).

---

## 6. Анти-паттерны (чего делать нельзя)

| ❌ Анти-паттерн | ✅ Как правильно |
|-----------------|------------------|
| Дать ИИ задачу «сделай X» и сразу принять результат | Пройти все 8 шагов workflow |
| Пропустить Шаг 3 (кросс-проверку ИИ) | Всегда просить ИИ перепроверить свою же постановку |
| Принять промпт без ручной проверки | Обязательно сверить промпт с бизнес-требованиями |
| Дать агенту выполнить весь промпт за один заход | Обязательные подтверждения после каждого шага |
| Не проверять код после каждого шага | Ручная проверка + сборка + тесты после каждого шага |
| Не отправлять сводку шага в чат | Отправлять для валидации соответствия промпту |
| Пропустить обновление документации | Обновлять DOCUMENTATION.md / Swagger / XML-doc |
| Коммитить без ревью | Ревью через `git diff` перед коммитом |

## 8. Артефакты

После завершения задачи в репозитории должны быть:

| Артефакт | Где хранится |
|----------|--------------|
| Постановка задачи | `docs/tasks/<task-id>.md` |
| Финальный промпт | `docs/prompts/<task-id>.md` |
| Сводки по шагам | в истории чата с ИИ (сохранять скриншотами/экспортом) |
| Реализация | в соответствующей ветке git |
| Обновления документации | `DOCUMENTATION.md`, Swagger, XML-doc |

---

## 9. Коммиты и ревью

- **Коммиты атомарные** — по одному шагу промпта.
- **Сообщение коммита** содержит ссылку на task-id и шаг.
- **Перед merge** — ревью `git diff` и проверка на соответствие промпту.

Пример сообщения коммита:
```
feat(appointments): add CostPrice to AppointmentService [TASK-042, step 3]

- Added CostPrice field
- Updated AutoMapper profile
- Migration: AddCostPriceToAppointmentService
```

- [ ] Шаг 3: кросс-проверка ИИ выполнена.
- [ ] Шаг 4: промпт составлен.
- [ ] Шаг 5: промпт проверен вручную.
- [ ] Шаг 6: правки внесены (если нужны).
- [ ] Шаг 7: финальная перепроверка ИИ пройдена.
- [ ] Шаг 8: реализация выполнена с подтверждениями.
- [ ] Все шаги отправлены в чат и валидированы.
- [ ] Проект собирается без ошибок.
- [ ] Тесты проходят (если есть).
- [ ] Код соответствует архитектуре.
- [ ] Документация обновлена.
- [ ] Коммиты атомарные и с описаниями.
